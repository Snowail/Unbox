## 2. 优先处理的缺陷

### P1-1：内层拒绝的条目被清零，缺文件仍可显示完全成功

**位置：** `src/UnzipWorker/main.cpp:639–652,1004–1009,1054–1071`；`src/UnzipWorker/WorkerExtractCallback.h:159–165`。

**实测：** 一个 PAX TAR 内含 `readme.txt` 和一个 623 字符的深层相对路径文件。直接提取 TAR 得到 `partial / exit 11 / unsafe_items=1 / extracted_items=1 / total_items=2`，源包应保留。对完全相同的 TAR 套一层 gzip 后，发布 Worker 得到 `ok / exit 0 / unsafe_items=0 / extracted_items=1 / total_items=2`。生产 WPF 最终显示“已完成 100%”，交付目录只有 `readme.txt`，没有说明漏项。

**原因：** 回调对不可解析的目的路径只增加 unsafe 计数，不设置提取错误；内层处理把 `result.unsafeItems` 固定写为 0，外层成功分支也没有累计内层计数。清单来自已经写出的条目，因此“清单与磁盘一致”不能证明“所有应提取条目均已交付”。同样的遗漏可以通过摘要校验。

**修复与验收：** 内外层共用完整的条目结果模型，保留并传播拒绝、用户跳过、策略过滤和失败原因；为每个计划条目记录终态。少一项必须成为 partial 或 failed，并禁止回收。将这个 TAR 和 TAR.GZ 成对跑到 WPF 最终提示、最终树及回收资格。此次没有观察到源包丢失；另一个身份比对缺陷当前会阻止正常回收，但不能依赖该缺陷来掩盖这里的错误资格判断。

### P1-2：原始名称解析忽略可靠 Unicode 元数据

**位置：** `src/UnzipWorker/ArchiveNames.h:102–114,154–185`；`src/UnzipWorker/main.cpp:365–377`。

**实测：**

| 样本 | 正确名称 / 对照结果 | 发布组件最终名称 |
|---|---|---|
| ZIP 名称字段为 `fallback.txt`，有效 `0x7075` Unicode Path 扩展记录为 `图.txt`，包含匹配的原名称 CRC | 7-Zip 列出 `图.txt` | `fallback.txt`，无编码询问，成功交付 |
| .NET `PaxTarEntry` 生成的 `path=Δ.txt` | 7-Zip 显示 `Δ.txt`，并识别 PAX / UTF-8 | `螖.txt`（U+8796），无编码询问，成功交付 |

ZIP 解析器只检查 bit 11，跳过了 extra 字段；TAR 解析器虽然读取 PAX `path`，却把 `declaredUtf8` 一律设为 false。之后这些较弱的原始名称结果覆盖引擎名称。bit 11 的回归已修好，但“已声明 Unicode 名称全部保留”尚未成立。ZIP 扩展字段的定义见 [PKWARE APPNOTE §4.6.9](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)。

**修复与验收：** 正确处理 Unicode Path 的版本、名称 CRC 与 UTF-8 内容；PAX 按记录边界解析 `path` 和字符集声明，并携带编码来源。不能识别可靠元数据时保留引擎给出的语义，不以简化解析结果覆盖。将上表两个样本加入最终目录逐字断言。

### P1-3：启发式解码仍会改写合法 GBK 名称，用户选择也不能覆盖

**位置：** `src/UnzipWorker/NameDecoder.h:124–144`；`src/UnzipWorker/main.cpp:811–814`。

**实测：** 不带 bit 11 的 GBK `茅.txt`，字节 `C3 A9`，在 `--cp 936` 下成功交付为 `é.txt`。7-Zip 使用 CP936 的对照名称是 `茅.txt`。进一步加入一条明确标成 UTF-8 的 `图.txt` 以触发编码选择：选择框中 CP936 示例为 `茅.txt`，通过 IPC 明确回答 CP936 后，仍落盘为 `é.txt`。

**原因：** `OnlyLatinSupplement` 仍将两字节歧义强行判为 UTF-8；3/4 字节分支同样没有区分自动猜测与用户明确指定。选择值等于当前代码页时又不重建计划；即使重建，还是同一套启发式逻辑。这也与 HANDOFF“两个字节的歧义保持代码页，不再猜测”的说明不符。

**修复与验收：** 区分自动模式与显式选择模式。可靠 Unicode 声明优先；对未声明名称，用户选定代码页后应严格按该值解码。预览与落盘必须调用同一路径。分别验证自动识别、显式 `--cp`、弹窗选择和记忆选择。

### P1-4：目录边界检查仍可被联接点绕过，并可能先在根外创建目录

**位置：** `src/UnzipWorker/PathSanitizer.h:181–213`；`src/UnzipProxy/Core/DeliveryManifest.cs:172–184`。

**实测前提：** 在测试暂存区内预置 `linked`，指向暂存区以外、但仍由本轮创建的空测试目录。这模拟暂存目录被其他本地进程修改；没有声称普通 ZIP 本身能创建 Windows 联接点。

- 归档仅含目录条目 `linked/`：`EnsureDirectory` 遇到已有目录直接返回 true，跳过句柄检查。发布 Worker 返回成功；生产完成处理也允许该联接点通过，最终交付的 `linked` 仍指向根外。
- 归档含 `linked/child/`：Worker 返回 access denied、退出 6，**但根外的 `child` 已实际创建**。原因是先沿字符串路径执行全部 `CreateDirectoryW`，最后才验证句柄；拒绝结果无法撤销此前的边界外副作用。

**修复与验收：** 已有目录也必须验证；创建每一级之前确认父目录的真实对象及归属，并在操作期间防止替换。交付验证和来源标记遍历应拒绝非预期 reparse point。两个样本都应失败且根外完全不变，不能只断言退出码非零。新增的普通文件句柄检查有价值，但不能替代目录及最终交付树的检查。

### P2-1：文件 ID 高低 64 位定义相反，正常源包被误判为替换

**位置：** `src/UnzipWorker/WorkerOpenCallback.h:177–192`；`src/UnzipProxy/Core/FileIdentity.cs:40–42`；`src/UnzipProxy/MainWindow.xaml.cs:1013–1015`。

**实测：** 同一个未修改的普通 ZIP，Worker 的 `FileIdHigh` 为非零、`FileIdLow` 为 0，C# 捕获结果恰好相反；卷号、长度、修改时间均一致，`Matches` 返回 false。通过发布 WPF 勾选回收，正文交付成功，但窗口显示“解压完成（源文件回收未完成）”，原因是“源文件在解压后已被替换或修改”。源包实际未被改动并仍在原位。

**原因：** Worker 把 `FILE_ID_128.Identifier[8..15]` 记为 low，C# 把 `Identifier[0..7]` 记为 low。原有真实回收测试使用 C# 自己捕获的快照，没有用 Worker 通过 IPC 返回的快照，所以 90/90 没有发现此问题。

**修复与验收：** 固定协议字节序，最好传输原始 16 字节的规范表示。用真实 Worker 快照执行完整回收路径；同时保留源包替换、修改和多卷混合结果反例。不要通过放宽身份比对来“修复”。

### P2-2：V7 TAR 被复合归档前置签名检查误拒绝

**位置：** `src/UnzipWorker/ArchiveNames.h:29–39`；`src/UnzipWorker/main.cpp:536–544`。

**实测：** .NET `V7TarEntry` 生成的 TAR 可被发布 Worker 单独正确交付，7-Zip `t` 也通过；gzip 封装后变为 `inner_not_tar / exit 10`，没有交付正文。

**原因：** `LooksLikeTar` 仅接受 ustar magic 或全零头，V7 TAR 没有 ustar magic；`requireTar` 在真正调用 TAR 引擎验证之前就将其拒绝。

**修复与验收：** 让 TAR handler 验证格式，或同时验证其他受支持的 TAR 头结构与校验和，不能把一种 magic 当作全部 TAR。相同正文的 V7、ustar、GNU、PAX 及空 TAR 应成对测试裸包和复合包；非 TAR 载荷仍须拒绝。

### P2-3：清单规范化裁掉合法前导空格，导致正常文件无法交付

**位置：** `src/UnzipProxy/Core/DeliveryManifest.cs:244–248`。

**实测：** ZIP 只含合法名称 ` leading.txt`。Worker 成功落盘，清单也如实记录前导空格；`NormalizeRelative` 的 `Trim()` 却把期望键改成 `leading.txt`，随后报告一个清单外文件和一个缺失文件。真实发布 WPF 显示“解压未完成”，保留暂存及源包，最终目录不生成。

**修复与验收：** 路径规范化只处理必要的分隔符和目录尾分隔符，不删除名称中的有效字符。分别测试文件、目录和折叠根的前导空格，以及空白名、非法尾随空格的既定处理策略。

### P2-4：重复目录条目进入清单后被当成冲突，正常 ZIP 整包无法提交

**位置：** `src/UnzipProxy/Core/DeliveryManifest.cs:138–141`；`src/UnzipWorker/WorkerExtractCallback.h:244–254`。

**实测：** ZIP 条目依次为 `folder/`、`folder/a.txt`、`folder/`、`folder/b.txt`。7-Zip 检测正常；Worker 正确写出两份正文并返回 ok。但同一个实际目录在清单出现两次，提交前校验报告“交付清单包含重复路径：folder”，整个交付失败。

**修复与验收：** 区分源归档条目结果和最终文件系统节点。相同实际目录的重复声明可合并；文件重复名、大小写冲突以及文件/目录类型冲突仍需严格处理，不能简单删除所有重复项检查。

现有 90 项可同时通过而本轮样本失败，主要有三处覆盖缺口：

1. 回收测试的身份由 C# 自捕获，未验 Worker → IPC → C# 的互操作；回收站摘要比对在没有落点时也会被记成 PASS（`tests/Tester/Program.cs:381–403`）。

3. 完成校验按已写出的清单验收，缺少原始计划条目对账；目录边界测试缺少已存在的联接点及“失败后根外无副作用”的断言。

下一轮应先补这些针对真实失败的回归，再修改实现。仅增加源码字符串检查或检查暂存目录非空，不能关闭本轮问题。
