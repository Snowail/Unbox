## 2. 按修复优先级排列的发现

### 01 · 发布阻断：有效归档可以解出零文件仍报告成功

**证据**：`src/UnzipWorker/SevenZipLibrary.h:203`、`:225`、`:246` 对三个探测分支都用 `SUCCEEDED(Open(...))` 且传入空的打开回调。7-Zip 使用 `S_FALSE` 表示该处理器未识别归档，这是一个非负返回值。代码因此会提前接受未打开归档的处理器。打开回调缺失还切断了打开阶段的密码和后续卷请求。提取阶段 `main.cpp:393` 也只检查 `FAILED(hr)`。本次两个假成功均在发布二进制上实测。出现 `ok` 后回收选项仍有效。[7-Zip 官方打开流程](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/UI/Common/OpenArchive.cpp)

**修复与验收**：按接口契约精确处理 `S_OK`、`S_FALSE` 和失败；支持打开阶段密码与按需取卷，读取归档警告、错误属性及逐项结果。用有效空包、正常非空包、加密头包、完整及缺卷包分别验收。合法空包须保留自己的成功路径，简单地禁用所有零条目归档会误伤它。

### 02 · 发布阻断：进入回收的条件没有证明输出完整

`WorkerExtractCallback.h:195` 把数据流的 CRC、SHA-256、字节数记入内存；`main.cpp:407` 最终仅取记录数量，未比对预期清单、已知文件大小或落盘摘要。7-Zip 自带的 CRC 或认证仍能发现部分归档错误，这无法证明暂存目录中每个最终文件都还在。创建空目录的错误也在 `WorkerExtractCallback.h:150` 被忽略。

`src/UnzipProxy/MainWindow.xaml.cs:330` 收到一条完成消息就进入提交，`:657` 移动目录，`:678` 开始回收；没有等待 Worker 退出码。Worker 自己在清理回调、关闭归档和释放输入流前就发出 `finished`（`main.cpp:421`）。普通成功时 UI 还丢弃回收结果。由此可能产生空目录后尝试回收，也可能因源文件仍被占用而回收失败、用户却看到完成提示。

**修复与验收**：以 Worker 退出 0、明确的任务完成消息、无归档或条目错误、输出清单一致、最终目录提交成功作为共同条件。要回收时核对已关闭文件的落盘内容及源文件身份，并在窗口分别显示解压和回收结果。对真实空目录、零字节文件、提交失败、Worker 异常退出以及用户明确允许过滤的条目建立各自的判定规则。

### 03 · 高：生产写入路径缺乏暂存根目录边界验证

`src/UnzipWorker/PathSanitizer.h:81` 的检测没有覆盖全部 Windows 根路径形式。未标为非法的名称由 `main.cpp:296` 直接保留；实际写盘在 `WorkerExtractCallback.h:146` 拼接路径后立即建目录或文件。没有统一校验最终打开的位置在暂存目录之内，也没有检查父目录重解析点。开发报告所称的 C# 与 C++ 双层前缀断言，在这条生产路径上没有执行。影响取决于格式处理器交付的名称及当前用户的文件权限。

**修复与验收**：所有条目由同一个 Worker 路径规划器产生相对目标；打开对象时校验受控根目录、路径组件和实际文件对象。用面向边界判定的单元测试和受控目录内的测试替身验收。只检查字符串的共同前缀不足以建立目录归属。

### 04 · 高：目标名碰撞会截断已经正确解出的文件

`src/UnzipWorker/FileStream.h:176` 对输出使用 `CREATE_ALWAYS`。大小写折叠、批量替换不合法字符或归档内重名，都可能把多个条目映射到一个 Windows 文件。逐条解码可以全部成功，最后目录里却只剩最后写入的数据。压缩包外层目录的“(2)”递增解决不了包内碰撞。

**修复与验收**：写盘前按目标文件系统语义检查条目到路径的一对一映射，包括文件与目录冲突；使用独占新建，在冲突时提示或分配稳定的新名字。用保留两份不同内容与两份摘要作为验收条件。

### 05 · 高：回收对象按名称猜测，且系统删除接口允许无法撤销的情况

`src/UnzipProxy/Core/ShellRecycleBin.cs:64` 把符合宽泛命名模式的文件整组加入。ZIP 分支（`:72`）甚至会为普通单包扫描同目录同名的卷后缀。没有由解码器实际读取的卷清单，也没有在执行前核对文件身份。三卷假成功使这个缺口直接关联到整组源数据。

`ShellRecycleBin.cs:109` 对介质判定异常默认放行。`:141` 组合 Shell 删除、尽可能允许撤销和静默确认。Windows 只为这个标志承诺“在可能时”保留撤销信息。返回错误时笼统声称源文件已保留，也不能说明部分多文件操作的逐项结果。[微软 Shell 删除标志](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shfileopstructw)

**修复与验收**：回收名单来自本次实际打开且验证过身份的输入卷；任何不确定项留在原处。使用经过验证且只执行回收的 Shell 路径，记录逐项结果。专门验收普通 ZIP 同目录存在无关同名分卷、设备不支持回收、回收站停用、源文件替换、部分回收失败，以及从回收站还原后逐卷摘要一致。[微软显式回收接口](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itransfersource-recycleitem)

### 06 · 高：损坏条目可能以普通最终目录交付，错误理由失真

`WorkerExtractCallback.h:212` 将 CRC 错误、错误密码、截断等一律压缩为一个布尔值；`main.cpp:413` 与“用户跳过非法名”合并成 `partial`。`MainWindow.xaml.cs:657` 在判断部分完成前提交暂存树，`:668` 将所有原因显示为字符非法。用户可能把损坏输出当作可用文件。密码传输还直接拼接 JSON（`MainWindow.xaml.cs:517`），对端用子串寻找结尾引号（`main.cpp:109`），含引号的合法密码不能正确往返。

**修复与验收**：把用户允许的跳过、密码错误、数据损坏、介质错误划成独立结果，保留文件名、卷名和原始错误码。损坏输出不发布到普通成功目录。密码使用同一套 UTF-8 JSON 序列化与解析器；明确的密码错误可重新打开并重试。修复等待响应标志在发请求之后才重设的竞态（`main.cpp:157`、`:318`）。

### 07 · 高：来源标记与资源上限没有落实

普通输出文件由 `FileStream.h:176` 直接创建，生产路径未见从下载源包传播 Windows 来源标记的步骤；这可能丢失后续程序用于判断文件来源的信息。另一个独立问题是流式写入并不会限制总输出量。`main.cpp:247` 收集预计大小，但写入回调没有可用磁盘空间、总输出字节或条目数量的预算，Job 也只配置退出联动。大量条目还会同时占用多份内存清单。开发报告据此声称具备解压炸弹防护，证据不足。

**修复与验收**：对支持来源标记的目标文件系统落实传递策略；给打开、列举、写盘分别设可解释的限额，可靠处理剩余磁盘空间，普通合法的大包允许用户决定是否继续。用受控的小额度测试验证中止、清理和保留源包。

## 3. 性能实测与优化次序

在同一台 i7-13700F Windows 机器、同一临时文件系统，使用同一份 7-Zip 26.06 DLL。对可复现的普通 ZIP 样本，各运行三次，每次写入一个新的空目录，第二轮交换运行顺序。计时含进程启动、解码、写盘及进程退出；计时后对每份输出逐文件核对预期 SHA-256，均通过。Worker 的 stdout 被持续读取，官方 CLI 关闭进度显示。测试没有启动 WPF、执行回收、清空系统缓存，也未测压缩率变化、RAR、多块 LZMA2 或网络盘。

| 工作负载 | Worker 三次耗时 | 官方 CLI 三次耗时 | 中位数对比 | Worker 进度帧 |
|---|---|---|---|---|
| 随机内容，单文件 64 MiB | 501 / 470 / 475 ms | 334 / 336 / 336 ms | 475 对 336 ms，耗时 1.41 倍 | 每轮 19 |
| 随机内容，1,200 个文件，每个 1 KiB | 2,132 / 2,085 / 2,206 ms | 551 / 502 / 506 ms | 2,132 对 506 ms，耗时 4.21 倍 | 每轮 1,201 |

1. **优先测哈希成本。** `FileStream.h:157` 对每次写入计算逐字节软件 CRC 和 SHA-256；`CryptoUtils.h:67` 为每个文件打开 CNG 算法提供程序。除引擎校验外，这两份额外摘要目前未用于回收决策。先纠正核验逻辑，再复用算法提供程序，按实际核验策略保留必要计算，用单变量对照测改善幅度。
2. **把进度限流落实到发端。** `main.cpp:373` 的条件允许每次换文件绕过 25 ms，`:70` 每帧同步刷新；UI 对每帧解析并复制 JSON。以固定节拍发最新的文件名和字节快照，完成、错误和询问继续立即发送。小文件样本可直接用每轮帧数和总耗时验收。
3. **进度和速度只使用同一口径。** `WorkerExtractCallback.h:108` 把引擎累计进度赋给计数器，`:162` 又将写盘字节加到同一个数。不同处理器会报告压缩或解压字节，计数可跳变或回退。另设独立的“成功写出字节”，由单调时钟采样。图表当前还会覆盖早期历史及人工加入波动（`SpeedGraphControl.cs:103`、`:218`），应让图反映实际吞吐。[7-Zip 进度回调约定](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/IArchive.h)
4. **减少小文件重复工作。** 规划时已读取目录属性，回调再次查询并反复创建相同父目录；索引连续却保存两份路径散列表，另建包含完整路径和摘要的结果列表。用按索引排列的条目计划，复用目录状态，只保存核验所需信息。验证资源释放对称性，输入流和总回调的初始引用后又额外 `AddRef`，使部分资源直到进程退出才释放。
5. **最后再调线程或换引擎。** 当前显式传给处理器的属性只有代码页，线程行为取决于引擎默认值与归档结构。本次基准不足以把耗时差归因于线程数、哈希或 IPC 中的某一项。先对上述三项分别做 A/B，再对大文件、多块 LZMA2/XZ、固实包和小文件包比较 1 线程与自动策略，同时记录 CPU、峰值内存和输出摘要。
