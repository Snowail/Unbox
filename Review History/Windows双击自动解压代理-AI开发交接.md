# Windows 11 双击自动解压代理 · AI 开发交接

规划日期为 2026-11-12。本文供需求方确认产品行为，也供下一位开发 Agent 实施和验收。本轮交付仅为设计文档。文中的程序名、脚本名和目录名均为拟议名称，性能数字均为建议验收目标。

## 1. 用户实际看到的流程

1. 用户把便携程序放到固定目录，运行一次“注册关联”脚本。脚本在当前用户的 Windows 默认应用中登记程序，并打开系统设置，由用户选择希望双击解压的扩展名。以后双击这些文件，或在“打开方式”中单次选择本程序，均直接开始，无需先打开压缩包浏览器。[微软默认应用平台](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/default-apps-platform)
2. 任务窗口立即显示“正在读取压缩包”。普通包自动继续。有加密时询问密码，有多种合理的文件名解码时提供真实名称预览。正常路径只需一次双击。
3. 结果放在源包旁边。例如 `发布包.zip` 内只有 `release-v2/docs/说明.txt`，按推荐规则得到 `发布包/docs/说明.txt`。用户可以暂停、继续或终止，在窗口内选择本次是否将源包移入回收站。
4. 内容写完并核对后，一次性显示最终目录。界面分别报告解压和回收结果。点击“打开所在文件夹”可定位结果。任务结束且窗口关闭后，程序和解压工作进程均退出。

## 2. 需要需求方决定的产品行为

以下推荐值用于说明后续设计；可按编号改选。第 1、2 项直接决定日常使用体验，第 3、4 项决定安装后能看到什么。

| 编号 | 需要决定 | 推荐值 | 另一选择及影响 |
|---|---|---|---|
| D1 | 压缩包有唯一顶层目录时，是否折叠它？目标重名怎么办？ | 只折叠最外面一层，目标统一用包名。目标已存在时另建“包名 (2)” | 保留包内顶层就会得到“包名/原目录”；也可选遇到重名时询问。按第 6 节示例决定 |
| D2 | “解压完成后移入回收站”是否记住？分卷和缺少内容校验的格式怎么办？ | 每次默认关闭；勾选后做写后回读。普通可核验的单包允许回收；整组分卷、缺乏归档内容校验依据的包默认保留 | 可记住上次勾选；可允许整组已核实的分卷回收；也可接受无内置校验的格式按“解码输出与落盘文件一致”回收。这三个选项可独立决定 |
| D3 | “全部格式”是否含办公文档、应用和程序文件的后缀？ | 登记全部归档、压缩流、镜像及分卷入口。能当容器读取的办公文档、安装包等单列为可选关联；普通可执行文件保留原有启动入口 | 可将所有系统允许关联的容器后缀都列为候选。Windows 对特定类型的限制须实测，并在清单逐项说明。所有模式均由用户指定默认程序 |
| D4 | `vhd(x).png` 的 `.vhx` 是自定义后缀，还是指 `.vhd`？ | 同时覆盖需求原文的 `.vhx`、`.vhdx` 和引擎原生 `.vhd`；对 `.vhx` 检测内容后选择处理器 | 如果是笔误则只保留标准 `.vhd`、`.vhdx` 这组映射。引擎列出的其他后缀（如 `.avhdx`）仍按一般图标规则处理 |
| D5 | “兼容 macOS 和 Linux”指这些系统制作的包，还是程序也在这两个系统运行？ | 首版 Windows 11 x64 应用，正确解出 macOS、Linux、Windows 制作的包；保留 Mac 辅助文件 | Windows ARM64 可另发原生包；若需要 Mac/Linux 原生应用，另设计其启动关联、文件系统、进度 UI 与回收站 |
| D6 | 对多义文件名，以及当前 Windows 目录无法忠实容纳的名称、链接等，如何处理？ | 编码预览供选择；对重名或无法还原的条目显示路径和原因，默认停止并保留源包 | 可选增加逐项改名或“仅提取可表示的文件”；一旦跳过条目，状态须显示“部分完成”，源包保留 |

## 3. 建议架构与开发工具

**采用 WinUI 3 原生任务窗口，配一个仅在任务期间存在的 C++ 工作进程，后台直接加载官方完整 `7z.dll`。** 两个进程分开，可以在解码器卡住时结束解压，仍由窗口准确说明源包和输出的状态。使用 DLL 回调可取得真实的密码请求、分卷请求和逐项错误。官方提供 `Client7z` 示例，创建对象无需在系统注册 7-Zip COM 组件。[7-Zip 开发 FAQ](https://www.7-zip.org/faq.html) · [官方调用示例](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/UI/Client7z/Client7z.cpp)

| 部件 | 建议工具 | 职责与边界 |
|---|---|---|
| 主程序 `UnzipProxy.exe` | Visual Studio、MSVC C++20、C++/WinRT、WinUI 3/XAML、Windows SDK、MSBuild | 解析资源管理器传入的路径、显示任务和对话框、监督 Worker、提交最终目录、调用系统回收站。解码和文件回读均在 UI 线程之外 |
| `UnzipWorker.exe` | 同工具链的原生 C++，使用与引擎版本对应的 7-Zip 头文件 | 打开和枚举归档、获取编码证据、规划条目路径、流式写入暂存区、验证。源归档和源分卷均以只读方式打开 |
| 引擎与发布 | 随包携带相同架构的官方 `7z.dll`，固定版本、记录出处和 SHA-256；WinUI 采用 unpackaged/self-contained，随包提供所需运行库 | 只从应用目录加载指定 DLL。在干净 Windows 11 普通账户验证便携包。规划基线为 26.06，官网发布记录与本机只读 `7z i` 一致；升级时重新生成格式清单和基准。[官方版本](https://github.com/ip7z/7zip/releases/tag/26.06) · [微软自包含部署](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps) |
| 脚本与构建资源 | Windows PowerShell 5.1 兼容脚本、构建期图像工具（如 Pillow）、多尺寸 ICO | 安装/卸载只处理关联与图标；用户机无需 Python、编译器或预装 7-Zip。发布包附匹配版本的 7-Zip 许可证、版权、对应源码链接与第三方署名。[7-Zip 分发许可](https://www.7-zip.org/license.txt) |
| 验证工具 | 原生单元/集成测试、同版官方 CLI、Windows Performance Recorder 或等效计时工具、干净的 Windows 11 测试账户 | CLI 作为独立对照，测试记录目录树、摘要、样本和系统版本。Explorer 关联、回收站还原和高 DPI 窗口需做系统级验证 |

**一次双击的生命周期**为“打开 → 等待密码或编码选择（按需）→ 规划路径 → 写暂存 → 核验 → 提交 → 按选择回收 → 退出”。主进程为每个任务建立私有双向管道，只向指定 Worker 传递端点和必要句柄；消息用任务 ID、请求 ID 配对。密码走独立的内存消息，不进入命令行、环境变量、日志或落盘状态。进度消息可合并，提问、错误、取消和完成消息要可靠送达。

主进程把 Worker 纳入启用 `KILL_ON_JOB_CLOSE` 的独立 Job Object，确保绑定完成后才开始工作。暂停、取消与 Worker 等待密码时的退出应由独立控制通道处理。连续双击同一源包时按卷和文件 ID 互斥；另一实例提示已有任务。不同包可同时启动，使用仅在任务期间存在的会话级资源上限控制同时活跃的 Worker，不需要服务、计划任务、托盘程序、开机启动项或 Explorer 扩展。[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

## 4. 引擎、多线程和性能选择

- 通过 DLL 导出函数枚举格式和处理器，按签名、扩展名和处理器 `Open` 结果识别；单独处理按后缀识别的格式和多处理器共用后缀的情况。由 `IInArchive` 读条目属性，用 `IArchiveExtractCallback` 提供按条目索引绑定的输出流。分别记录打开结果、归档级错误/警告和解压结果。总体 `HRESULT` 成功仍可能伴随某一条目 CRC 错误。[格式导出](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/ArchiveExports.cpp) · [归档接口](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/IArchive.h)
- 对支持线程属性的处理器，启用自动多线程，并在基准中比较单线程和受限线程数；记录处理器接受的设置及实际 CPU 时间。LZMA2 有独立数据块、XZ 有多个块时有机会并行；单个依赖前文的压缩流无法靠指定更多线程等比例提速。固实包按引擎次序一次提取，避免为并发取不同文件而反复解码前面的数据。[7-Zip 多线程解码记录](https://www.7-zip.org/history.txt)
- 先优化一次解码、顺序写入、复用缓冲区和消息节流。普通解压不默认先跑一遍 `7z t`。勾选回收时，将写后回读单列为“正在校验”，让用户看到额外耗时。海量小文件、机械盘以及同时读写同一设备都应单独测量。
- **可选的更快方案**仅针对普通、未加密的 ZIP/Deflate 独立小条目：用成熟的 ZIP 目录读取库配合 `libdeflate`，在总内存预算内按条目并发。它本身只负责压缩流，也没有流式接口。大条目、分卷、加密、Deflate64 和其他方法继续走 7-Zip。备用引擎必须共享路径规则、逐项 CRC、输出校验及取消逻辑。仅在代表性样本端到端耗时有可重复收益时再采纳，首版推荐只交付 7-Zip。[libdeflate 项目说明](https://github.com/ebiggers/libdeflate)

**基准交付**：同机同盘、同一批归档，在独立空目录分别运行官方 7-Zip、代理默认模式、代理勾选回收的校验模式。样本含单个大文件的 ZIP、数万小文件 ZIP、单块/多块 LZMA2、多块 XZ 和固实 RAR；标记 SSD/HDD、缓存状态、线程数。每组至少三次，报告耗时中位数、输出 MiB/s、峰值内存、CPU、首个窗口出现时间及输出摘要。建议初始目标为大包普通模式的中位耗时不超过同版官方解压的 1.15 倍；单独列出 UI 冷启动、写后校验和文件系统瓶颈。以上没有实测速率或加速倍数。

## 5. 文件名编码与跨系统兼容

目标是让归档中的“資料/設計図.pdf”在 Explorer、其他 Unicode 程序和跨平台传输中保持相同可读字符。名称模型使用 Unicode；计划清单、可复制诊断或其他文本输出使用 UTF-8。Windows 文件 API 使用宽字符路径，NTFS 保存 Unicode 名称。压缩包里每个文件的内容按原字节解压，不对文本文档进行转码。[Windows 文件名字符集](https://learn.microsoft.com/en-us/windows/win32/intl/character-sets-used-in-file-names)

| 名称来源 | 判断依据 | Agent 实现要求 |
|---|---|---|
| 7z、RAR5 等有明确 Unicode 名称的格式 | 采用格式或引擎明确提供的 Unicode 名称 | 保留字符、emoji 和组合音标；已明确定义的 Unicode 条目免于整包代码页覆盖 |
| ZIP 有编码信息 | bit 11 指定 UTF-8；Info-ZIP Unicode Path 字段 `0x7075` 含版本、原始名称 CRC 和 UTF-8 名称 | 严格校验 UTF-8；接受有效版本且名称 CRC 匹配的扩展字段。字段过期则忽略它；有效标记互相冲突、目录记录不一致时转入预览或报结构错误。[PKWARE APPNOTE §4.6.9 及附录 D](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) |
| 传统 ZIP、无编码标记的 TAR 或旧格式 | 保留原始名字节；ASCII 名在候选编码中相同时直接通过。非 ASCII 试严格 UTF-8、GBK/CP936、GB18030、Big5/CP950、日文 CP932、CP437 等 | 按字节往返、多个条目的共同证据、格式来源及候选可读性排序。合法 UTF-8 或系统语言单独出现时均不足以解决多义性。可行解码产生不同名称且证据薄弱时，弹出选择框 |
| macOS / Linux 的 TAR | 识别 PAX 路径、字符集声明、GNU 长名及老 TAR 原始字节 | 明确的 Unicode 路径优先；原始或标记为二进制的路径走字节判断。按实际目标文件系统处理大小写及路径冲突，保留可表示的原始 Unicode 拼写。[7-Zip TAR 实现](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/Tar/TarHandler.cpp) |

**获取名字节是第一阶段的原型重点。** 26.06 ZIP 的 `kpidPath` 已经是引擎转换后的名称。ZIP 应从受边界检查的目录元数据取得原始名、标志、偏移及扩展字段，或采用能暴露这些字段的成熟库；解码内容仍交给 7-Zip。验证 ZIP64、分卷及名称重复时，元数据记录能与同一源快照的引擎条目一一对应。其他旧格式优先验证其代码页参数、是否需重新打开、是否能得到不同的真实预览；缺少原始信息时，显示实际限制和可行选项，不能从已经乱码的字符串“逆推”后悄悄写盘。需逐格式记录支持方式，旧格式的手选恢复也需实样验收。[7-Zip ZIP 名称读取实现](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/Zip/ZipHandler.cpp)

**选择框**显示候选名称和代码页编号、若干含非 ASCII 字符的真实相对路径，以及“其他代码页”。切换选项立即重算预览及同名冲突；展示内容要和最终路径一致。选择只影响当前任务里尚未判定的条目。混合编码包若单一选择无法覆盖，支持分组选择，或在不支持的组上停止并指出条目；取消发生在正式输出前。macOS 的 `__MACOSX`、`._*` 和 `.DS_Store` 可能携带数据，推荐作为普通条目保留。NFC/NFD 可用于提示跨平台等价冲突，原名和目标路径均须可核对。

## 6. 目录规则、复合格式和分卷

推荐把“只有一层目录”解释为**所有条目共有一个最外层目录**。由显式目录和文件的路径前缀共同推断，根部的普通文件也参与判断；只折叠一次，保留下层树。压缩包名去掉最长的已识别后缀；保留版本号中的点。

| 打开的源包 | 包内示例 | 推荐的最终结果 |
|---|---|---|
| `照片.zip` | `照片/a.jpg` | `照片/a.jpg` |
| `项目.zip` | `release/src/main.c`，没有单独的目录记录 | `项目/src/main.c` |
| `附件.zip` | `a.pdf` 和 `图/b.png` | `附件/a.pdf`、`附件/图/b.png` |
| `阅读.zip` | 唯一文件 `说明.txt` | `阅读/说明.txt` |
| `备份.tar.gz` 或 `备份.tgz` | 外层 gzip，内层 TAR 只有 `备份/data/x` | `备份/data/x` |
| `日志.txt.gz` | 单 gzip 数据流 | `日志.txt/日志.txt`；若包内有可信、合法的原名则采用该原名。单文件外层命名受 D1 约定 |
| `项目.7z.001` 或 `项目.part01.rar` | 多卷组成一个归档 | 整组只有一个 `项目/` 输出；首卷定位和缺卷提示见下文 |
| `资料.zip` | `资料/a` 和 `__MACOSX/._a` | 有两个根，得到 `资料/资料/a` 与 `资料/__MACOSX/._a`；保留元数据会影响折叠判定 |
| `空包.zip` | 无条目，或唯一空目录 `old/` | 经引擎确认是有效空包后创建 `空包/`；唯一空目录折叠后同样保留一个空目录 |

- 只对约定的复合封装（如 `.tar.gz`、`.tar.bz2`、`.tar.xz`、`.tar.zst` 及别名）自动展开到 TAR 内容，并核验内外两层。外层如需生成可寻址中间文件，放在任务暂存目录，计入可用空间；普通 ZIP 内的其他压缩包保留为文件。磁盘镜像按引擎可枚举的层级交付，支持的文件系统内容或仅能导出的分区镜像写进格式矩阵。
- 区分字节切分的 `.7z.001`、RAR 的 `.partNN.rar`/旧式 `.rar+.r00`，以及分卷 ZIP 的 `.z01 … .zip`；入口按格式规则定位，不能一律取名字典序第一项。只拼接有格式或命名证据的同一组；普通 `.001` 也可能只是被切分的非归档流。卷名只在原目录内解析。提示准确缺失的卷；证据不足时显示预期命名模式。
- 使用源包同一卷上的独占暂存目录。完整写入及核验后，以不覆盖现有项的同卷重命名提交。目标重名时递增后缀并重试，处理两份同名任务并发提交。只读源目录或空间不足时提示选择可写目标，改在该目标卷暂存。取消只清理本任务创建且可验证归属的暂存文件；崩溃遗留可在下次相关任务中提示清理。
- 写盘前检查路径越界、绝对路径、Windows 保留名、卷名、冒号/备用数据流、末尾点或空格、文件和目录同名、大小写/规范化冲突及重解析点；写入时再次验证根目录和父目录边界。普通文件和空目录应忠实保留，符号/硬链接、设备节点、权限等不能按选定策略还原时列出详情并保留源包。对已有下载来源标记按 Windows 行为处理，归档自带的特殊条目不能决定暂存目录以外的写入位置。

## 7. 密码、错误、进度和终止

| 时机 | 窗口与引擎行为 |
|---|---|
| 读取加密头或解压加密条目 | 打开与提取回调都提供 `ICryptoGetTextPassword`。请求绑定到当前任务，可显示/隐藏输入。用户取消即取消整项。明确密码错误可重试，重新打开或重建对应的提取状态，丢弃失败输出；已解出的不同条目不能与失败尝试混合提交 |
| 解压错误 | 将条目索引、路径、阶段、原始操作结果、归档警告、HRESULT/Win32 错误及当前卷收集到可复制的详情。区分 CRC、截断、缺卷、不支持的方法、磁盘满、无权限和目标被占用。加密条目只给出数据错误时，文案用“密码可能错误，或数据已损坏”，同时给出重试和取消。[7-Zip 错误枚举](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/IArchive.h) |
| 正常进度 | 主视图显示包名、目标、百分比、当前文件、已写/预计大小、速度、剩余时间、暂停/继续、强制终止、回收勾选框。详情区显示近 60 秒的速度面积图。遵循系统明暗主题、强调色、高对比度、键盘和屏幕阅读器，适配 100%–200% DPI |
| 速度与百分比 | 每约 250 ms 采样实际成功写入的输出字节，以单调时钟算差值，单位 MiB/s；短滑窗平滑。分母使用同口径的预计输出字节，未知时显示不定进度。7-Zip 的某些流格式回报压缩输入字节，避免与解压大小混用。读取复合封装、写出最终文件及回读分别计数，完成标志以提交成功为准。[进度回调说明](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/IArchive.h) |
| 暂停与继续 | 在输入/输出流和进度回调设置协作暂停点。按钮先显示“正在暂停”，Worker 确认在途写入停稳后显示“已暂停”；暂停期间 ETA 冻结。继续时剔除暂停时长。引擎长时间未回调时保留终止入口，不用挂起任意线程来模拟暂停 |
| 强制终止或关闭 | 先发取消并唤醒等待中的回调，短时无响应则结束该任务的 Job，等待句柄关闭后清理暂存。写入或核验期间终止，源包保留且不出现最终目录。原子提交及已交给 Shell 的回收操作有明确的不可撤销瞬间；此时显示实际状态，提交后取消后续回收，不移除已完成结果 |
| 小包很快完成 | 任务立刻开始，窗口可短延时显现以减少闪烁；若任务已结束，回收保持默认关闭。错误、密码和选码交互立即可见。即使窗口未展开，最终结果遵循同一套核验与提交规则 |

## 8. 完整性与源包回收

**回收的依据是“本次完整结果已经落盘并提交”。** UI 主进程是唯一发起回收的部件。任一阶段失败都保留源文件；“解压完成，源包已保留”和“解压完成，源包已移入回收站”是两个独立的完成状态。

1. 打开时记下源文件及实际读取的分卷身份（卷和文件 ID、长度及修改时间）；在读取过程中防止被写入或替换。在同一源快照上枚举、取名和解压。磁盘父镜像等辅助依赖不进入源卷回收清单。
2. 对每个预期条目记录应到达的相对路径、类型、长度（若已知）、引擎结果、实际写入长度及归档提供的校验依据。成功须覆盖普通文件、零字节文件及目录；所有流已完成写入和关闭，磁盘错误、跳过、缺卷、校验错误、警告或工作进程异常都阻止自动回收。固实块、外层流以及加密格式的认证结果按处理器实际粒度记录。
3. 勾选回收时，在写出时计算文件摘要，关闭后重新打开实际输出文件，逐文件核对 SHA-256、长度、清单及可用的归档 CRC/认证。为允许中途勾选，可从首字节起始终计算写流摘要；回读只在需要时执行。锁定回收选择的时点要在窗口可见。无内置内容校验的格式（如普通 TAR）可证实落盘与解码输出一致，却无法证明入包前的数据完好；按 D2 推荐值保留源包，并给出原因。
4. 主进程取得验证清单，确认所有条目通过后提交最终目录，并确认提交的是已验证的同一棵树。回收前再次核对当前源身份与目标状态；路径被替换、输出变动或文件系统不能提供所需保证时保留源包。不通过文件名通配符寻找待回收文件。
5. 采用 Windows Shell 的仅回收语义。原型优先验证显式 `ITransferSource::RecycleItem` 在本地文件系统的支持与返回项；采用 `IFileOperation` 时设置 `FOFX_RECYCLEONDELETE`，验证每项结果、取消状态以及回收站中的新项目。先验证该环境不会降级为永久删除；网络共享、回收站关闭、超容量或不支持该操作时直接保留并说明。验收包含“从回收站还原并比对源包摘要”。分卷如获准整组回收，先核对所有卷，再逐卷记录；若部分失败，显示已回收和仍在原处的确切卷名。[显式回收接口](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itransfersource-recycleitem) · [回收标志](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags) · [逐项结果](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-postdeleteitem)

### 9.1 完整格式清单的生成

构建时针对随包 DLL 通过 `GetNumberOfFormats` / `GetHandlerProperty2` 导出处理器及扩展名，与同一发行包的 `7z i` 对照。形成一份清单，字段至少有「处理器、扩展名/别名、归档层级、是否有效入口、关联策略、图标来源、测试样本」。格式、扩展名和编码器是三个概念：`(.tar)` 等注解用于解释内层名称，普通文件关联使用最后一个后缀；多个处理器共享的 `.img` 或 `.apk` 只登记一次。无独立后缀、内部占位、系统限制以及仅用于散列的项分别注明原因。升级时对照差异，新增真实归档类型要有对应图标和验收记录。[引擎处理器属性定义](https://github.com/ip7z/7zip/blob/26.06/CPP/7zip/Archive/IArchive.h)

2026-11-12 在本机只读列出的 26.06 x64 样例，供核对分类；正式安装清单由交付版本生成，不能把这一表当白名单。

| 类别 | 实际观察到的例子 | 建议关联策略 |
|---|---|---|
| 归档、压缩流及封装 | 7z、RAR/RAR5、ZIP/ZIPX、TAR、gzip、bzip2、XZ、Z、Zstandard、LZMA、LZH/LHA、AR、ARJ、CAB、CPIO、DEB、RPM、XAR、WIM | 覆盖全部可关联的归档后缀，以及实际支持的复合别名与分卷入口。Zstandard 对应 `.zst`、`.tzst`；不能因主站简表或图标目录未列出就漏掉 |
| 磁盘、镜像、文件系统 | ISO、UDF、DMG、APFS、HFS、EXT、FAT、NTFS、SquashFS、GPT、MBR、QCOW、VDI、VHD、VHDX、VMDK | 按需由用户选为默认，双击后提取可读内容。ISO、VHD 等原有系统挂载操作对用户有价值，安装时保留其默认选择 |
| 同时具有其他主要用途的容器 | ZIP 还列出 `.jar`、`.docx`、`.xlsx`、`.epub`、`.apk`；Compound 列出 `.msi`、`.doc` 等；PE 列出 `.exe`、`.dll`、`.sys` | 按 D3 决定在系统允许范围内展示哪些候选。解析能力可经显式选文件入口使用。任何条目均不得改写程序执行类的全局打开命令 |
| 无法单凭后缀区分或不属于压缩包 | 多种镜像共用 `.img`，数字后缀可能只是分片，Hash 行列的是摘要文件 | 共用扩展按内容识别。Hash 作为能力记录，不登记成自动解压格式；不能识别时显示原因，源文件保留 |

### 9.3 注册与取消注册脚本的行为

| 位置（当前用户） | 内容 |
|---|---|
| `HKCU\Software\Classes\<本程序专用 ProgID>` | 类型说明、`DefaultIcon`、`shell\open\command`。每种要区分图标的后缀有稳定的 ProgID。命令形如 `"<固定绝对路径>\UnzipProxy.exe" "%1"`，使用 Unicode 路径和独立参数 |
| `HKCU\Software\Classes\.<ext>\OpenWithProgids` | 增加本程序 ProgID 候选值，保留已有候选及扩展名默认值 |
| `HKCU\Software\<产品专用键>\Capabilities` 及 `FileAssociations` | 应用名、用途说明、应用图标、各后缀到 ProgID 的映射 |
| `HKCU\Software\RegisteredApplications` | 专用注册名指向相对 `Software\…\Capabilities` 路径，供“默认应用”列出程序 |

`注册关联.ps1` 从脚本位置解析应用与图标绝对路径，检查发布内容齐备，幂等写入，通知 Shell 刷新关联（`SHChangeNotify/SHCNE_ASSOCCHANGED`），打开 `ms-settings:defaultapps?registeredAppUser=<编码后的注册名>`；系统不支持深链时打开默认应用首页。应用移位后可从新位置重跑脚本更新路径。用户可通过系统设置或“打开方式 → 始终”选择默认，脚本不写 `UserChoice` 或其哈希。[默认应用设置深链](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-default-apps-settings) · [微软文件类型注册](https://learn.microsoft.com/en-us/windows/win32/shell/fa-file-types)

`取消关联.ps1` 按安装清单移除本应用拥有的 ProgID、候选值、Capabilities 及 RegisteredApplications 中的本应用值，随后通知 Shell；共享键中如有第三方值则保留。重复执行、部分安装失败和升级时丢弃旧扩展名均可恢复。用户若将本程序选为默认，卸载后通过系统选择其他程序，脚本不承诺恢复某个历史默认应用。安装和卸载均以标准用户权限运行。解压结果和源包独立于程序目录。
